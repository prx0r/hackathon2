# Live demo — two agents, same task, same fault

Run:

```bash
cargo run -p iolaus-demo -- --port 8080
```

Open `http://127.0.0.1:8080`.

## Scene 1 — CRM silent write

Click **CRM silent write**.

Both agents call a real local HTTP action service backed by SQLite.

The service deliberately returns:

```json
{"success": true, "customer_id": "alice"}
```

without inserting the row.

### Left: baseline agent

Expected timeline:

```text
ROUTE     create_customer
EXECUTE   HTTP 200 / success=true
TRUST     outcome=success
CHAIN     send_welcome(alice)
CHECK     independent ground truth = customer missing
RESULT    FALSE TRUSTED SUCCESS
```

### Right: verified agent

Expected timeline:

```text
ROUTE     create_customer
EXECUTE   HTTP 200 / success=true
STATE     SUCCEEDED_UNVERIFIED
VERIFY    GET /crm/customers/... = missing
REJECT    postcondition false
BLOCK     send_welcome requires verified_customer:alice
RESULT    safe rejection
```

## Scene 2 — deployment false green

The tool reports successful deployment but the health endpoint is unhealthy.

Baseline records success and announces completion.

Iolaus probes health and rejects the transition.

## Scene 3 — upload accepted, not indexed

HydraDB's ingestion-oriented cookbooks explicitly distinguish upload from verified indexing.

The benchmark service returns `accepted=true` while status remains `queued`.

Baseline proceeds to recall.

Iolaus polls the independent status endpoint and blocks until ready.

## Scene 4 — financial evidence gate

The answer generator emits a plausible answer with zero chunks.

Baseline treats "generated" as success.

Iolaus requires a minimum evidence cardinality before the answer can be promoted.

Then run the same case with evidence and watch it pass.

## 90-second talk track

> HydraDB is very good at remembering what agents did and learning from execution outcomes. That makes one missing boundary important: what exactly counts as a successful outcome?
>
> Both agents are executing the same task against the same HTTP service. The service says success—but the customer was never written.
>
> The baseline trusts the tool response, records success, and runs the dependent step.
>
> Iolaus does not call that failure immediately. It calls it `SUCCEEDED_UNVERIFIED`, then checks the declared postcondition through an independent read path. The row is absent, so the transition is rejected and the dependent step is blocked.
>
> On a healthy run the exact same verifier passes, a signed receipt is emitted, and only then is success eligible to become HydraDB learning signal.
>
> The full benchmark repeats this as paired trials across fragile seams from HydraDB's own cookbooks. The metric we add is false trusted-success commit rate.
>
> HydraDB asks what the agent should do. Iolaus asks when we are allowed to believe it worked.
